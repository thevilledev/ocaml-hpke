Ciphersuites

Each registry is a closed OCaml variant, not an integer. Unknown codepoints cannot be constructed at all; of_int is the only way in from the wire, and it returns Unsupported_algorithm for anything outside the tables below. 

let suite =
  Suite.create ~kem:Kem.X25519 ~kdf:Kdf.Hkdf_sha256
    ~aead:Aead.Aes_128_gcm

let exporter =
  Suite.export_only ~kem:Kem.P384 ~kdf:Kdf.Hkdf_sha384

Eight KEMs, three KDFs, and three AEADs give 72 encryption suites; every one of them is round-tripped by the test suite in Base mode. Dropping the AEAD gives 24 further export-only suites.

Sizes are bytes. A Diffie-Hellman KEM encapsulates to an ephemeral public key, so its encapsulated key has the size of a public key; ML-KEM encapsulates to a ciphertext, which has a size of its own, and a hybrid KEM to that ciphertext followed by an ephemeral group element. Kem.public_key_size, Kem.private_key_size, Kem.encapsulated_key_size, and Kem.supports_auth report these at run time.

ML-KEM

Kem.Mlkem512, Kem.Mlkem768, and Kem.Mlkem1024 are the post-quantum KEMs of FIPS 203, as draft-ietf-hpke-pq defines them for HPKE, provided by the pure OCaml mlkem. With an HKDF they run the RFC 9180 key schedule unchanged, in the Base and PSK modes. What differs from a Diffie-Hellman KEM:

  • No Auth or AuthPSK mode. ML-KEM has no authenticated encapsulation, so the auth functions return Unsupported_mode. The PSK mode, or a signature over the encapsulated key and ciphertext, authenticates the sender instead.
  • A private key is a seed. It is the 64 bytes d || z that FIPS 203 generates a key pair from, not the expanded decapsulation key. Every 64-byte string is one.
  • Decapsulation does not fail. An encapsulated key of the right length that was tampered with, or made for another key, yields a secret unrelated to the sender's and no error (implicit rejection). The receiver is set up, and the failure surfaces as Open_error at its first open.
  • The specification is a draft. Encodings are those of FIPS 203 and are not expected to move, but derive_key_pair follows revision 05 of the draft and changes if the draft does. The draft prefers ML-KEM-768 and ML-KEM-1024 to ML-KEM-512, as a hedge against cryptanalysis that weakens ML-KEM without breaking it.

Hybrid KEMs

Kem.Mlkem768_p256, Kem.Mlkem768_x25519, and Kem.Mlkem1024_p384 are the post-quantum/traditional hybrid KEMs of draft-ietf-hpke-pq, as draft-irtf-cfrg-concrete-hybrid-kems defines them. Each runs ML-KEM and an elliptic-curve exchange side by side and hashes both secrets together with SHA3-256, so a message stays protected as long as either half holds. Kem.Mlkem768_x25519 is X-Wing. They work in the Base and PSK modes as ML-KEM does, and differ from it in what follows from the second half:

  • A private key is a 32-byte seed. SHAKE256 expands it into an ML-KEM seed and a scalar. P-256 and P-384 draw the scalar by rejection sampling, which fails with negligible probability.
  • Keys and encapsulations have two halves. A public key is the ML-KEM key followed by the group element, an uncompressed SEC1 point or an X25519 public value; an encapsulated key is the ML-KEM ciphertext followed by an ephemeral element.
  • The element is validated. A tampered ML-KEM ciphertext decapsulates to an unrelated secret, but an element that is not on the curve, or an X25519 value of low order, is Invalid_encapsulation. The concrete draft leaves the X25519 value unchecked; no honest peer produces one that is refused.

One-stage KDFs

Hpke.Draft_hpke_04, the module of the successor draft, has a KDF registry of its own: the three HKDFs above, with which its suites are the RFC 9180 suites of the same identifiers, and the one-stage SHAKE KDFs of draft-ietf-hpke-pq, which exist only in the successor's key schedule.

Deliberate omissions

  • A wire format. encapsulated_key and ciphertext stay separate fields. The library will not invent a framing that applications would then have to live with forever.
  • Compressed points. NIST public keys must be in uncompressed SEC1 form, which is what RFC 9180 specifies.
  • TurboSHAKE KDFs. draft-ietf-hpke-pq also defines TurboSHAKE128 and TurboSHAKE256, which take a Keccak permutation of 12 rounds that neither mlkem nor Digestif provides yet. The library implements no primitive of its own.
  • Expanded ML-KEM private keys. Only the 64-byte seed is accepted, the one format draft-ietf-hpke-pq defines.
  • Secret printers and equality helpers. Private keys and PSKs have no pp and no comparison function, so they cannot casually reach a log line or a timing-variable comparison.

Validation

What is checked, and where
Public keysExact encoded length. NIST keys must start with the uncompressed SEC1 marker and lie on the curve. X25519 and X448 low-order values are rejected when the key is used. ML-KEM keys must pass the modulus check of FIPS 203: every coefficient reduced.
Private keysExact encoded length. NIST scalars must be non-zero and below the curve order, compared in constant time. X25519 and X448 scalars are clamped on parse and on output. Every ML-KEM seed of the right length is valid.
Encapsulated keysFor a Diffie-Hellman KEM, parsed as a public key. For ML-KEM, exact length only: decapsulation does not fail. Context-level setup reports a failure structurally; single-shot opens normalize it.
Suite agreementA recipient or sender key whose KEM differs from the suite's KEM yields Key_mismatch before any cryptography, and an Auth or AuthPSK call on an ML-KEM suite yields Unsupported_mode before that.
PSKsSecret of at least 32 bytes and a non-empty identifier. A length check cannot establish entropy.
Derivationderive_key_pair follows RFC 9180, including rejection sampling for the NIST curves; exhausting it yields Derive_key_pair_failure. For ML-KEM it follows draft-ietf-hpke-pq and derives the seed with SHAKE256.

Limits

  • A context's sequence number is 96 bits. When it is exhausted, seal and open return Message_limit_reached instead of reusing a nonce.
  • Plaintexts are bounded per AEAD, as tabulated above; longer input returns Plaintext_too_long.
  • A ciphertext shorter than the AEAD tag is rejected as Open_error without consuming a nonce.
  • Exports run from 0 to 255 times the KDF hash size, and never change sequence state.

Versioning

Wire behavior lives under Hpke.Rfc9180 and will not be changed by a future HPKE standard. A successor standard can be added as a second versioned module, so applications choose when to move rather than discovering that an upgrade changed what their peers see.

The successor draft, draft-ietf-hpke-hpke, removes the Auth and AuthPSK modes and reserves their identifiers. They stay in Hpke.Rfc9180; the successor's module does not offer them.

That module is Hpke.Draft_hpke_04, revision 04 of the draft. It offers the Base and PSK modes, over every KEM, and the one-stage KDFs. It shares keys, AEADs, PSKs and contexts with Hpke.Rfc9180, and with an HKDF produces exactly what Hpke.Rfc9180 does. A revision of the draft that changes the wire gets a module of its own.
